#### 1. WebSocket client `get_printer_last_task` crashes on mixed finished/running tasks
- **Lens:** DRY Violations (diverged duplicate)
- **Files:** `custom_components/elegoo_printer/websocket/client.py:227-247, 284-302`
- **Severity:** High
- **Confidence:** High (bug empirically reproduced during deep-dive)
- **Problem:** Both `get_printer_last_task()` and `async_get_printer_last_task()` select the latest task with `return task.end_time or 0 if task else 0`. A task with `end_time=None` (running job or the `None` placeholder from `_print_history_handler`) collapses to `int 0` while completed tasks retain a `datetime`, so `max(keys, key=...)` compares `int` vs `datetime` → `TypeError` whenever one finished and one unfinished task coexist in `print_history`. The cc2 and mqtt copies of the identical logic use the correct form (`task.end_time.timestamp() if task and task.end_time else 0.0`); git shows ws never had it (independent implementations, ws form dates to the SDCP split #192, mqtt born correct in #261). Reachable today via `api.async_is_thumbnail_available()` → `async_get_current_print_thumbnail()` and via the public `async_get_task(include_last_task=True)` contract, so it is latent (no current entity triggers it) but live for the API. No test covers any of the six variants.
- **Proposal:** Two 3-line hunks in `websocket/client.py` adopting the existing cc2/mqtt `sort_key` (order-preserving: `None→0.0`, `datetime→.timestamp()`), plus a ~48-line regression test file (`websocket/tests/test_last_task_sort.py`, mirrors the existing `test_gcode_proxy_fetch.py` `_make_client` pattern; cases: mixed end times [true regression catcher], all-None, identical [tie-break pins]). Do not touch the cc2/mqtt copies. Effort ~5 min; risk negligible (replaces the line with the form already shipping in two other clients).

#### 2. WebSocket listener dies on malformed payloads with a leaked exception; cc2 `disconnect()` can re-raise a stored listener exception
- **Lens:** Weak Abstractions (error handling divergence)
- **Files:** `custom_components/elegoo_printer/websocket/client.py:133-150, 593, 608-635, 726-732`, `custom_components/elegoo_printer/cc2/client.py:436-439`
- **Severity:** High
- **Confidence:** High (mechanics verified against the tree)
- **Problem:** (a) Live bug: ws `_status_handler` calls `PrinterStatus.from_json` unguarded and `_parse_response` catches only `JSONDecodeError`, so a malformed status payload (e.g. firmware shape change → pydantic `ValidationError`, a `ValueError` that is *not* caught) propagates out of the message loop, is re-raised as `ElegooPrinterConnectionError`, and kills the listener. The task has no done-callback and `disconnect()` cancels it without awaiting, so every death leaks an un-retrieved task exception. Recovery exists (coordinator reconnects) but a persistent malformed payload causes a 30 s die→offline→reconnect loop. (b) Latent hazard: cc2's outer listener only catches `CancelledError` + the MQTT tuple; a non-MQTT exception (e.g. from `_deep_merge`) terminates the task, and `disconnect()`'s `await` (wrapped in `suppress(CancelledError)` only) re-raises it to the caller, skipping the remaining teardown (event unblock, client close) → unhandled exception in an HA handler + half-teardown. (c) The ws death is logged at DEBUG with `str(e)` — no traceback.
- **Proposal:** Small hardening PR *before* any structural refactor, two commits: (1) ws — per-message `try/except Exception: logger.exception(...)` guard around `_parse_response` inside the loop, plus `contextlib.suppress(CancelledError): await self._listener_task` in `disconnect()` (~8 lines + import); (2) cc2 — wrap the listener await in `disconnect()` with `except Exception: logger.exception(...)` so a terminal listener exception can never escape (~4 lines). Reviewer-verified diffs exist for both. TDD repro: feed a malformed status frame, assert the listener survives and `disconnect()` returns cleanly. Fixes (a)+(c); (b) separately.

- **Files:** `custom_components/elegoo_printer/cc2/client.py` (1486 L), `mqtt/client.py` (951 L), `websocket/client.py` (858 L)
- **Severity:** Medium
- **Confidence:** High (line-by-line comparison completed during deep-dive)
- **Problem:** `ElegooCC2Client`, `ElegooMqttClient`, `ElegooPrinterClient` share large byte-identical machinery — the SDCP `_send_printer_cmd` framing + event registry, `_print_history*`/`_print_video` handlers, the UDP discovery skeleton, the `disconnect()` unblock/clear/close/reset skeleton, and the 9-attribute `__init__` state block — and the drift has already produced F1 (sort key), F2 (ws missing cancel-await), an inline `timeout=10` in mqtt/ws vs a named constant in cc2, a latent ws `IndexError` in `_parse_response` (unguarded `topic.split("/")[1]`), and divergent status-payload extraction (mqtt's nested→flat chain vs ws passing the full frame into `PrinterStatus.from_json`'s `data.get("Status", data)` shim). cc2 is a genuinely different wire (own ID scheme, registration, heartbeat, delayed disconnect) and its shared blocks are only the plumbing.

Net ≈ −480 lines code, +300-400 test lines. **Stage 3 (optional, deferred)** — cc2 adopts only the plumbing (state init, background-task helper, unblock/clear contract); its 5-stage `disconnect()`, int registry, and wire handlers stay. Do NOT unify: per-transport `connect_printer()` state machines, `is_connected` semantics, the gcode-proxy scheduling (ws keyed retry scheduler vs cc2 fire-and-forget + on-device detail are deliberately different strategies; the shared `GCodeProxyClient` HTTP layer is the correct seam).

#### 5. Connection-state and failure semantics differ across the three clients and only cc2 is hardened
- **Lens:** Inconsistent Patterns
- **Files:** `cc2/client.py:121-128, 190-194`, `mqtt/client.py:116-125`, `websocket/client.py:113-128, 133-145`
- **Severity:** Medium
- **Confidence:** High
- **Problem:** `is_connected` means three different things: ws = connected AND socket open; mqtt = connected AND client object exists; cc2 = connected AND registered AND client exists. Only cc2 has the hardening primitives added by the 2026-06-29 plan (generation/stale-callback guard, delayed-disconnect grace window, heartbeat loop); ws and mqtt clear state, have no stale-callback protection and no— cc2-only `check_health`. Disconnect flows diverge (F2 is one instance); message dispatch is a substring `in` check in cc2 vs `match/case` on topic/payload in mqtt/ws. The per-transport state machines are defensible, but the *contract* (unblock waiters on disconnect, await the listener, a documented `is_connected` invariant per transport) is currently only there by accident in one client.
- **Proposal:** Standardize the shared contract in the Stage 1 hardening PR (F2) — uniform "unblock waiters + await listener (with the F2 guard) + reset flags" sequence with a `_transport_open()` hook for the per-transport part of `is_connected` — and pin the existing per-transport invariants with characterization tests (Stage 1) so the Stage 2 base class has a documented contract to implement rather than one rediscovered per class. Keep `connect_printer()`/heartbeat/delayed-disconnect per-transport (deliberate difference, pinned by tests).
